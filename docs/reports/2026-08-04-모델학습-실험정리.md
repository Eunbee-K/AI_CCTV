# 모델 학습 실험 정리 (detect_v1 ~ v5) 및 향후 계획

**정리일** 2026-08-04 · **대상 기간** 2026-06-29 ~ 2026-08-03
**자료** `E:\AI_CCTV_RESULTS`(결과) · `E:\AI_CCTV_DATASET`(데이터 메타) · `configs/sweeps`(스윕 설정)

지금까지 진행한 YOLO 학습 실험 **5단계**를 목적과 확인 사항 중심으로 정리했다.
수치는 남아 있는 `results.csv`·`args.yaml` 실측 기준이다.

> **읽기 전에 — 이 실험들의 성격**
>
> - GPU는 본사 AX혁신실 장비를 **빌려 쓰는 것이라 사용 시간에 제약이 있다.**
>   본학습이 아니라 실험 학습이므로, 확인하려던 것이 확인되면 종료하고 다음 실험으로 넘어갔다.
>   **에폭을 다 채우지 않은 것은 대부분 실패가 아니라 의도된 중단이다.**
> - 학습이 끊기고 재개되는 과정에서 일부 기록이 유실됐다.
> - 데이터셋은 용량 문제로 **파일명만 엑셀로 남기고 실물은 삭제하는 구조**다.
>   이 방식도 중간부터 시작해 앞쪽 실험은 목록이 없다.
>
> 따라서 이 보고서는 완결된 학습 기록이 아니라 **각 단계에서 확인된 것**을 남기는 데 목적이 있다.

**현재 앱에 배포된 모델은 없다.** v1~v5 모두 실험 단계다.

## 3. 단계별 상세

### v1 — 학습 환경 구축과 파라미터 탐색 (2026-06-29경)

결함 1종(CL) 약 1,000장 규모로 **YOLO 사용 환경을 구축하고 학습 방법을 익히는 것**이 목적.
해상도 같은 파라미터 값을 확인했다.

- **데이터**: train 11,000 / val 1,800 / test 4,549 = 17,349장, 전부 클래스 0(`crack`)
  (파일명 기준: CL 16,454 · 미분류 균열 895)
- **모델**: `yolo11l.pt`, batch 16, lr0 0.01, patience 30

| run | imgsz | batch | cache | cos_lr | 에폭 | best mAP50 | 시간 |
|---|--:|--:|:--:|:--:|---|--:|--:|
| `1000test` | 640 | 16 | ✗ | ✗ | 98/100 | 0.787 | 0.20h |
| `1000test-2` | 640 | 16 | ✗ | ✗ | 130/200 | 0.792 | 0.27h |
| `1000test-3` | 1280 | 16 | ✗ | ✗ | 98/100 | 0.756 | 0.77h |
| **`1000test-4`** | **960** | 16 | ✗ | ✗ | 92/100 | **0.808** | 0.44h |
| `960-2` | 960 | −1(auto) | ✓ | ✓ | 40/70 | 0.674 | 3.71h |

**확인된 것 — 해상도는 960이 최적.** 640(0.787) → 960(0.808) → 1280(0.756)으로, 1280은 오히려
떨어지면서 시간만 1.8배 더 걸렸다. **이후 모든 실험이 960을 쓰는 근거**가 된 결과다.

`960-2`만 batch auto(−1) + `cache`·`cos_lr`을 켠 조합인데 0.674로 낮고 시간은 8배 걸렸다.
셋 중 무엇이 원인인지는 이 기록만으로 가릴 수 없다. 에폭 70 종료는 최고점 ep40 + patience 30에
따른 정상 조기종료다.

### v2 — 데이터 규모 검증 (2026-07-10)

v1의 학습 데이터가 너무 적었기 때문에 **각 16,000장 규모가 충분한지**, 그리고 **결함 종류를
늘리면 정확도가 어떻게 되는지** 보려던 실험.

- **설정**: `yolo11l.pt`, imgsz 960, batch auto, cache ✓, cos_lr ✓, 50에폭 완주
- **결과**: best ep34 — **mAP50 0.821 / mAP50-95 0.597** / P 0.775 / R 0.780
- **시간**: 7.96시간 (에폭당 9.5분)

**확인된 것** — 남아 있는 실험 중 mAP50·mAP50-95 모두 최고다. 클래스 2종에 각 16,000장이면
0.82 수준이 나온다는 기준선을 얻었다.

> 데이터셋 실물과 split 수·클래스 번호는 워크스테이션에만 있어 확인되지 않았다.
> 실험명의 `16000`도 이름에서 온 값이라 검증되지 않았다.

### v3 — 결함 항목 확대 (2026-07-10~29)

v2의 연장선으로 결함 항목을 5종(BK·LP·JF·JD·DS)으로 늘려본 실험.

- **데이터**: train 80,000 / val 10,000 (워크스테이션 전용)
- **설정**: imgsz 960, batch 4, cos_lr ✓, 설정 50에폭
- **진행**: 26에폭에서 세션 단절(퇴근 후 **누군가 컴퓨터를 끔**) → legacy 경로로 재개해 42에폭까지 간 뒤 수동 중지
- **결과**: mAP50 0.759 / mAP50-95 0.570 / P 0.721 / R 0.731

**확인된 것 — 클래스별 편차가 크다.** 이것이 v5 실험 계획의 근거가 됐다.

| 클래스 | DS(토사퇴적) | LP(연결관-돌출) | JD(이음부-단차) | BK(파손) | JF(이음부-손상) |
|---|--:|--:|--:|--:|--:|
| mAP50 | 0.942 | 0.939 | 0.822 | 0.600 | **0.495** |

LP·DS는 0.94로 실사용 가능한 수준인데 **JF는 0.495로 절반에도 못 미친다.** 평균 0.759라는
숫자 하나만 보면 놓치는 부분이고, **항목별로 골라 써야 한다**는 방향이 여기서 나왔다.

### v4 — 학습 자동화 시스템 검증 (2026-07-30)

v5를 돌리기 전에 **학습을 자동화하는 시스템을 구축**하고, 그 시스템이 제대로 도는지 확인하는 것이
목적. 학습 규모를 줄여 **20시간 안에 끝나도록** 구성했다.

- **구성**: bbox 18클래스 — train 52,992 / val 6,629 / test 6,628 = 66,249장
  (데이터가 풍부한 10개 클래스만 65%로 축소, 부족한 클래스는 원안 유지)
  + seg 10클래스 17,928장을 이어서 돌리는 계획
- **결과**: bbox가 **24/50 에폭에서 오류로 중단**. mAP50 0.615 / mAP50-95 0.413
- **시간**: 5.59시간 (에폭당 14.0분) — 50에폭 완주 시 약 11.7시간, 사전 산정 13.1시간과 부합

**확인된 것** — 자동화 시스템 자체는 동작했고 소요 시간 예측도 맞았다. 목적을 달성했으므로
**나머지 학습은 진행하지 않는다.**

이어서 돌기로 했던 seg(`test4_seg_20h_260729`)는 **결과 폴더 자체가 없다.** bbox가 중단되면서
시작되지 못한 것으로 보인다.

### v5 — 본격 학습 (2026-08-03 완료)

확보된 학습 데이터가 **1,000장 이상인 결함 항목**(유의미한 결과가 나올 만한 것들)을 18개로
추려 본격 학습. seg 데이터가 있는 항목도 함께 테스트했다.

| 구분 | 설정 파일 | 클래스 | 데이터 | 학습 |
|---|---|--:|---|---|
| bbox | `test3_18class.yaml` | 18 | train 133,992 / val 16,749 / test 16,748 = **167,489장** | imgsz 960, 50에폭 |
| seg | `test4_seg.yaml` | 10 | train 21,979 / val 2,800 / test 2,800 = **27,579장** | imgsz 960, 50에폭 |

bbox 18종: BK · CC · CL · CM · DS · HL · JD · JF · JS · LP · LS · PO · RT · SD · SG · TO · PJ · IN
seg 10종: CL · CC · SD · BK · LP · JF · JD · DS · PJ · IN

**학습이 정상 완료된 것까지 확인(08-03).** v4에서 만든 자동화 시스템이 제대로 돌아간 결과다.

> **지표는 아직 확보하지 못했다.** 결과가 워크스테이션에만 있고 이 외장하드
> (`E:\AI_CCTV_RESULTS`)에는 복사되지 않았다. **v6 계획을 세우려면 v5의 클래스별 정확도가
> 반드시 필요하므로, 다음 본사 방문 때 가져와야 한다.**

### 기록이 어긋나는 부분 2건

**v3 — `results.csv`에 앞 29에폭이 없다.** 재개하면서 새 폴더에 기록이 시작돼 에폭 30~42의
13행만 남았다. 메타데이터의 `best_epoch: 35`와 CSV의 ep30은 **서로 다른 값이 아니라 다른 범위를
보고 있는 것이다.**

**v2 — best epoch가 메타(ep47)와 실측(ep34)이 다르다.** CSV는 1~50에폭이 온전하므로
실측(ep34, mAP50 0.82117)이 맞다. 메타의 ep47은 근거를 알 수 없다.

### 스윕 상태 파일이 "running"으로 남아 있다

v4의 `test3_18class_20h_260729_sweep01.state.json`이 아직 이렇다:

```json
{ "runs": { "test3_18class_20h_260729_960_e50": {
    "status": "running", "started_at": "2026-07-30T09:59:58+09:00", "error": null } } }
```

실제로는 24에폭에서 멈췄다. 프로세스가 죽으면 상태가 `running`인 채 남아 **아직 돌고 있는 것처럼
보인다.** v5가 잘 돌았으니 급한 문제는 아니지만, 나중에 이 파일만 보고 판단하면 오해할 수 있다.
