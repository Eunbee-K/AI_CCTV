## 2. 실험별 상세

### detect_v1 — 균열 1종 (2026-06-29경, 5 run)

파이프라인 검증과 입력 해상도 탐색이 목적. 데이터는 실물 없이 파일 목록만 보관되어 있다
(`AI_CCTV_DATASET/detect_v1/manifests`).

- **데이터**: train 11,000 / val 1,800 / test 4,549 = **17,349장**, 전부 클래스 0(`crack`)
  (파일명 기준 내역: CL 16,454 · 미분류 균열 895)
- **모델**: `yolo11l.pt`, batch 16, lr0 0.01, patience 30

| run | imgsz | batch | cache | cos_lr | 에폭 | best mAP50 | mAP50-95 | 시간 |
|---|--:|--:|:--:|:--:|---|--:|--:|--:|
| `1000test` | 640 | 16 | ✗ | ✗ | 98/100 | 0.787 | 0.486 | 0.20h |
| `1000test-2` | 640 | 16 | ✗ | ✗ | 130/200 | 0.792 | 0.464 | 0.27h |
| `1000test-3` | 1280 | 16 | ✗ | ✗ | 98/100 | 0.756 | 0.412 | 0.77h |
| **`1000test-4`** | **960** | 16 | ✗ | ✗ | 92/100 | **0.808** | 0.480 | 0.44h |
| `960-2` | 960 | −1(auto) | ✓ | ✓ | 40/70 | 0.674 | 0.437 | 3.71h |

**해상도는 960이 가장 좋았다.** 640(0.787) → 960(0.808) → 1280(0.756)으로, 1280은 오히려
떨어지면서 시간만 1.8배 더 걸렸다. 이후 실험이 전부 960을 쓰는 근거가 된 결과다.

`960-2`는 같은 해상도인데 **성능이 0.674로 낮고 시간은 8배(3.71h)** 걸렸다. 다른 run과 달리
batch를 auto(−1)로 두고 `cache`·`cos_lr`을 켠 조합이다. 셋 중 무엇이 원인인지는 이 기록만으로는
가릴 수 없다. 에폭이 70에서 멈춘 것은 최고점이 ep40이고 patience가 30이라 조기 종료된 것으로,
설정대로 동작한 결과다.

### detect_v2 — BK·DS 2종 (2026-07-10, 1 run) — 현재 배포 모델

- **데이터**: 워크스테이션에만 있음(`/home/workstation/ai_cctv/260709_test2/dataset`).
  split 수와 클래스 번호는 **미확인**. 실험명의 `16000`은 이름에서 온 값일 뿐 검증되지 않았다
- **설정**: `yolo11l.pt`, imgsz 960, batch auto, cache ✓, cos_lr ✓, 50에폭 완주
- **결과**: best ep34 — **mAP50 0.821 / mAP50-95 0.597** / P 0.775 / R 0.780
  (최종 ep50: mAP50 0.819 / mAP50-95 0.598)
- **시간**: 7.96시간 (에폭당 9.5분)

전체 실험 중 **mAP50·mAP50-95 모두 최고**다. 클래스가 2종뿐이라 유리한 조건이기도 하다.

### detect_v3 — BK·LP·JF·JD·DS 5종 (2026-07-10~29, 1 run)

- **데이터**: 워크스테이션 전용, train 80,000 / val 10,000
  (실험명의 `16000`은 클래스당 장수에서 온 이름으로 추정)
- **설정**: imgsz 960, batch 4, cache ✗, cos_lr ✓, 설정 50에폭
- **진행**: 26에폭에서 세션 단절 → legacy 경로로 재개해 42에폭까지 간 뒤 **수동 중지**
- **결과**(메타데이터 기록, best.pt val 재실행): mAP50 0.759 / mAP50-95 0.570 / P 0.721 / R 0.731

**클래스별 편차가 크다:**

| 클래스 | LP(연결관-돌출) | DS(토사퇴적) | JD(이음부-단차) | BK(파손) | JF(이음부-손상) |
|---|--:|--:|--:|--:|--:|
| mAP50 | 0.939 | 0.942 | 0.822 | 0.600 | **0.495** |

LP·DS는 0.94로 실사용 가능한 수준인데 **JF는 0.495로 절반에도 못 미친다.** BK도 0.600으로 낮다.
평균 0.759라는 숫자 하나만 보면 놓치는 부분이다.

### 18class 스윕 — 18종 (2026-07-30, 1 run) — **중단됨**

20시간 예산에 맞춰 데이터가 풍부한 10개 클래스만 65%로 줄여 구성한 파이프라인 검증용 스윕
(`configs/sweeps/test3_18class_20h_260729.yaml`).

- **데이터**: 18클래스 · train 52,992 / val 6,629 / test 6,628 = **66,249장**
  - 풍부한 클래스(BK·CC·CL·DS·JD·JF·LP·SD·PJ·IN): 각 train 3,900
  - 부족한 클래스: RT 440 · SG 505 · TO 544 · PO 664 · CM 617 · HL 886 (LS만 7,036으로 많음)
- **설정**: `yolo11l.pt`, imgsz 960, batch auto(실측 8), 설정 50에폭
- **결과**: **24에폭에서 중단** — mAP50 0.615 / mAP50-95 0.413 / P 0.603 / R 0.614
- **시간**: 5.59시간 (에폭당 14.0분)

에폭당 14분 실측이므로 50에폭 완주에는 **약 11.7시간**이 필요했다. 설정 파일의 사전 산정은
13.1시간이었으니 예측은 맞았고, 학습이 중단된 것이 문제다.

## 3. 정리하며 발견한 것

### [중단 방치] 스윕 상태 파일이 "running"으로 멈춰 있음

`test3_18class_20h_260729_sweep01.state.json`이 아직 이렇게 남아 있다:

```json
{ "runs": { "test3_18class_20h_260729_960_e50": {
    "status": "running", "started_at": "2026-07-30T09:59:58+09:00", "error": null } } }
```

실제로는 24/50 에폭에서 멈췄고 그 뒤 갱신이 없다. 세션이 끊기거나 프로세스가 죽으면 상태 파일이
`running`인 채로 남아, 나중에 보면 아직 돌고 있는 것처럼 보인다. **재개(resume) 여부를 판단할 때
이 파일을 믿으면 안 된다.**

`weights/last.pt`가 남아 있어 24에폭 시점부터 이어서 학습할 수 있다.

### [기록 불일치] detect_v3 — results.csv에 앞 29에폭이 없음

`results.csv`에 **에폭 30~42의 13행만** 있다. 재개(resume)하면서 새 폴더에 기록이 시작돼
앞부분이 이 파일에 없다.

| | 메타데이터 기록 | results.csv 실측 |
|---|---|---|
| best epoch | 35 | 30 (CSV 범위 내) |
| best mAP50 | 0.75946 | 0.76086 |

메타데이터 쪽이 전체 학습 이력이나 val 재실행 기준으로 보이고, CSV는 재개 이후 구간만 담고 있다.
**두 값이 다른 것이 아니라 서로 다른 범위를 보고 있는 것이다.**

### [기록 불일치] detect_v2 — best epoch가 다름

| | 메타데이터 기록 | results.csv 실측 |
|---|---|---|
| best epoch | 47 | **34** |
| best mAP50 | 0.82016 | **0.82117** |

CSV는 1~50에폭이 온전히 있으므로 실측(ep34, 0.82117)이 맞다. 메타데이터의 ep47은 근거를 알 수 없다.

### [자료 부재] detect_v2·v3 데이터셋이 로컬에 없음

둘 다 `record_type: metadata_only`이고 실물은 워크스테이션에만 있다. detect_v2는 **split 수와
클래스 번호조차 확인되지 않았다.** 재현하거나 이어서 학습하려면 워크스테이션 접근이 필요하다.

`configs/detect_v2.yaml`의 `names: {}`가 아직 비어 있는 것도 같은 이유다.
