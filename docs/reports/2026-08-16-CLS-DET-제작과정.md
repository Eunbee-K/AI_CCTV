# 배포 모델 제작 과정 — 분류기(CLS)와 검출기(DET)

**작성** 2026-08-16 · **대상** `apps/AI_CCTV/assets/`에 실제로 들어간 두 모델

앱에 붙어 있는 두 판독기를 **어떤 데이터로 · 어떤 설정으로 · 어떤 결과가 나왔는지**
각각 정리한다. 구조와 두 모델의 관계는
[결함분석기 시스템 구조](2026-08-16-결함분석기-시스템구조.md)를 먼저 볼 것.

| | CLS | DET |
|---|---|---|
| 역할 | 결함 구간 선별 + 1차 이름 | 위치(박스) + 2차 이름 |
| 모델 | EfficientNet-B0 (24클래스 분류) | YOLO11-L (18클래스 검출) |
| 파일 | `assets/classifier.onnx` (15MB) | `assets/best.pt` (49MB) |
| 학습 위치 | Colab T4 | 워크스테이션 RTX 5090 |

## 1. CLS — 분류기 (EfficientNet-B0)

### 1.1 학습 데이터

**`clsdata_old_v6_multiclass`** — 24클래스(결함 23종 + 정상 1종), train 11,495장.

만드는 순서는 두 단계다. 먼저 이진 데이터셋(`clsdata_old_v6`)을 구성하고,
그것을 결함코드별 폴더로 재배치한다.

```bash
python build_old_v6.py        # 1. 이진(정상/결함) 데이터셋
python build_multiclass.py    # 2. 코드별 폴더로 재배치 (--normal-ratio 0.30)
python resize_dataset.py      # 3. 384px 사본 (Colab 업로드용, 원본 보존)
```

**train 구성 (11,495장)**

| 결함 | 장수 |
|---|---|
| BC BK CC CL CM DF DG DS HL JD JF JS LD LP LS PO RT SD SG TO (20종) | 각 **400** |
| ETC | 438 |
| IF | 336 |
| DE | 68 |
| **정상(normal)** | **2,653** (결함 전체의 30%) |

**설계에서 정한 것 두 가지**

- **결함을 종류당 400장으로 맞췄다.** 원본이 종류마다 400~42,000장으로 극심하게
  불균형해서, 그대로 쓰면 흔한 종류만 배운다. 400장을 못 채우는 3종(DE 68 ·
  IF 336)은 있는 만큼만 넣었다.
- **정상을 결함의 30%로 줄였다.** 이진에서는 1:1이었는데, 다중 클래스에서는
  정상이 한 덩어리라 결함 23종을 합친 것과 맞먹는다. 그대로 두면 "일단 정상"
  쪽으로 쏠려 종류를 가르는 힘이 준다.
- **정상의 20%를 관 밖(맨홀·지상 전경)으로 채웠다.** 이전 버전(v3)은 관 밖을
  한 장도 안 보여줘서 관 밖을 39% 결함으로 오판했다. 이 구성으로 **0%**가 됐다.

**val (1,494장)** — 야장(실제 조사영상) 기반, 18클래스. train과 관로 단위로 분리.

> **val의 한계** — 야장에 있는 종류가 편중돼 있다(RT 1장 · SG 1장 · HL 2장).
> 학습 중 지켜보는 값으로만 쓰고, **종류별 성능은 별도 판으로 잰다**(§1.3).

### 1.2 학습 설정

`train_multiclass.py`, Colab T4에서 실행.

| 항목 | 값 | 이유 |
|---|---|---|
| 백본 | EfficientNet-B0 (ImageNet 사전학습) | 15MB로 작아 앱에 얹기 좋다 |
| 입력 | **384×384** | 224보다 결함이 잘 보인다. 원본은 최대 1280×720 |
| epochs | 24 (최종 채택 20) | |
| batch | 32 | 384px에서 64는 T4 OOM |
| optimizer | AdamW, lr 3e-4, weight_decay 1e-4 | |
| scheduler | CosineAnnealingLR | |
| loss | CrossEntropy, label_smoothing 0.05 | |
| 샘플링 | **WeightedRandomSampler (1/√n)** | 400장을 못 채운 종류가 남아 있어 보정. √로 완만하게 — 68장짜리 DE가 과대표집되면 그것만 외운다 |
| 증강 | RandomResizedCrop(0.7~1.0) · 좌우반전 · ColorJitter(0.3) | **상하반전은 쓰지 않는다** — 토사퇴적처럼 중력 방향에 의미가 있는 결함이 있다 |

**체크포인트를 세 가지로 저장한다** — 무엇을 최적화할지가 용도마다 다르기 때문이다.

| 파일 | 기준 | 배포 |
|---|---|---|
| `best_acc.pt` | 다중 클래스 정확도 | **← 채택** |
| `best_binF1.pt` | 이진 환산 F1 | |
| `best_recall.pt` | 정상 오탐 5%에서의 결함 재현율 | |

### 1.3 결과

**학습 지표 (epoch 20, 야장 val 기준)**

| | 값 |
|---|---|
| 다중 클래스 정확도 | 0.706 |
| 이진 환산 F1 | 0.942 |
| 오탐 5% 지점 재현율 | 0.810 |

**성능 실측** — 야장 val은 종류 편중이 심해 별도 판으로 다시 쟀다.

`testset_bycode`(23종 각 20장 + 정상 200장, S20/AIHub) 기준:

| | 값 |
|---|---|
| **AUC** | **0.9906** |
| 결함 재현율 (정상 오탐 5%) | **96.0%** (437/455) |
| 이름 정확도 (붙인 것 중) | **95.2%** (219/230) |
| 이름을 붙인 비율 | 50.5% (확신 0.9 이상만) |
| 정상에 잘못 붙인 이름 | **0/200** |

교차 확인 — `valset_bycode`(야장 78%)에서 **AUC 0.9856**. 두 판이 비슷해
도메인에 크게 흔들리지 않는다.

**결함코드별 탐지율** (정상 오탐 5% 지점) — 23종 전부 80% 이상:

| 탐지율 | 종류 |
|---|---|
| **100%** (14종) | BC CM DE DF DG HL IF JS LD LS PO RT SG TO |
| 95% | CC JF LP SD |
| 90% | CL DS JD |
| 80% | BK ETC |

**정상 오탐** — IN 5% · PJ 7% · **관 밖 0%**(v3는 39%였다)

**이름 정확도는 종류마다 크게 갈린다.** DF·DG·IF는 100%인데 JS는 0%다.
이음부 계열(JS·JF)과 BK(파손)는 사진 한 장으로 종류를 가르기 어렵다 —
단차를 재야 아는 판정이라 구조적 한계로 본다.

### 1.4 배포

```bash
python export_multiclass_onnx.py --ckpt <best_acc.pt>
```

ONNX로 내보내는 이유는 앱에 torch(2GB)를 안 깔기 위해서다 — onnxruntime은
50MB고 CPU 추론도 더 빠르다. 원본과 최대 차이 **5.72e-06**으로 검증했다.

**클래스 이름표(`classifier.classes.json`)를 함께 저장하고, 없으면 모델을 아예
열지 않는다.** 인덱스와 코드가 어긋나면 조용히 틀린 이름을 붙인다(YOLO-cls
실험에서 train 24종 / val 18종이 밀려 실제로 겪었다).

## 2. DET — 검출기 (YOLO11-L, test3)

### 2.1 학습 데이터

**`test3_18class`** — 결함 16종 + 맥락 2종(PJ·IN), train 133,961장.

`configs/sweeps/test3_18class.yaml`에 클래스별 quota와 소스를 적어두면
`scripts/sweep`가 외장하드 원본에서 정확히 그만큼 모아 임시 데이터셋을 만든다.

| 클래스 | train quota | 소스 |
|---|---|---|
| BK CC CL DS JD JF LP SD | 각 12,000 | 서울시 S20/S22 + AIHub |
| PJ IN (맥락) | 각 12,000 | AIHub |
| LS | 7,036 | S20/S22 (보유 전량) |
| JS | 3,300 | S20/S22 (보유 전량) |
| HL | 886 · PO 664 · CM 617 · TO 544 · SG 505 · RT 440 | S20/S22 (보유 전량) |

**데이터가 적은 종류는 보유 전량을 넣었다.** 그래서 검증할 사진이 남지 않아
나중에 유출 없는 평가가 불가능해졌다(§2.3의 한계).

**분할** — `split_seed: 42`로 클래스마다 결정적으로 셔플해 train/val/test를 자른다
(`deterministic_pick`). 시드가 고정이라 **나중에 "그때 무슨 파일을 썼는지"를
재현할 수 있고**, 실제로 그 목록(`used_files.csv`)이 결과 폴더에 남는다.

### 2.2 학습 설정

| 항목 | 값 |
|---|---|
| 모델 | YOLO11-L (`yolo11l.pt` 사전학습) |
| 입력 | **960** (사전 실험: 640/960/1280 중 960이 최고) |
| epochs | 50 (best epoch 46) |
| batch | 8 (수동 고정 — AutoBatch가 RTX 5090에서 4로 과보수 추정) |
| optimizer | auto, lr0 0.01, warmup 3 epochs |
| scheduler | cosine (`cos_lr: true`), patience 30 |
| 증강 | mosaic 1.0 (마지막 10epoch 해제) · 좌우반전 0.5 · 회전 0 |
| 소요 | 약 28.8시간 |

### 2.3 결과

**학습 지표**

| | 값 |
|---|---|
| mAP50 | **0.703** |
| mAP50-95 | 0.493 |
| precision / recall | 0.697 / 0.654 |

**성능 실측** — 유출 없는 판(`test3_holdout`, 야장 80%)에서:

| | 값 |
|---|---|
| 이름 정확도 | 36.0% (105/292) |
| 정상 오탐 (PJ, 야장) | 13.0% |

**탐지율**(이름 무관, 뭐라도 검출) — 이름 정확도와 크게 다르다:

| 코드 | 탐지 | 이름 |
|---|---|---|
| HL | **100%** | 0% |
| LP · SD | 100% | 70~80% |
| TO | 95% | 80% |
| LS | 85% | 30% |
| CL | 90% | 85% |
| CM | 35% | 0% |
| JS · JD | 20% | 0~10% |

**이름을 못 붙이는 것과 못 보는 것은 다르다.** HL은 이름 0%인데 탐지 100%다.
lead 구조에서는 탐지만으로도 행이 만들어져 값어치가 있다.

### 2.4 왜 test3인가 — test5에서 교체한 이유

test5(17종)가 먼저 배포돼 있었고 `testset_bycode`에서 이름 정확도 90.0%였다.
그런데 같은 종류를 야장 기준으로 재니 **33.3%**로 무너졌다.

원인을 `used_files.csv`로 확인했다:

| 대조 | 겹침 |
|---|---|
| `testset_bycode` 결함 455장 ∩ test5 train | **259장 (56.9%)** |
| 같은 판 ∩ test3 학습분 | 249장 (54.7%) |
| `test3_holdout` 492장 ∩ test3 학습분 | **0장** |

**그 판의 절반 이상이 모델이 학습 때 본 사진이었다.** 90%는 일반화가 아니라
암기를 잰 값이다. test3는 학습분을 재현·제외한 판에서 36.0%로, test5의 야장
기준(33.3%)보다 높아 교체했다.

**교훈** — 검증셋을 만들 때는 반드시 `used_files.csv`와 먼저 대조할 것.
비교는 `source_path`의 파일명으로 한다(`dest_filename`은 접두어가 붙어 있어
그대로 비교하면 겹침 0으로 나온다).

## 3. 두 모델을 같은 판에서 비교

지금까지 두 모델을 각각 다른 판에서 쟀다 — 학습분이 달라 한쪽에 깨끗한 판이
다른 쪽에는 유출된 판이었다. **`common_holdout`은 두 학습분 186,014장을 모두
제외해 만든 첫 공통 판이다**(겹침 0 자동 검증, 결함 12종 360장 + 정상 200장).

| | 값 |
|---|---|
| DET 이름 정확도 | 61.7% |
| CLS 이름 정확도 | 40.8% |
| **합집합** | **90.3%** |
| 겹침 | 12.2% |

**61.7% → 90.3%로 28.6%p 오르고 그 이득이 전부 CLS 단독분이다.** 겹침이
12.2%뿐이라 두 모델이 거의 다른 사진을 맞힌다.

**다만 상호보완의 실체는 "담당 범위가 다른 것"이다.**

| 구간 | CLS | DET |
|---|---|---|
| 둘 다 아는 8종 | 18.3% | **92.5%** |
| CLS만 아는 4종 (BC DF DG LD) | **85.8%** | 0% (클래스 없음) |

같은 종류를 두고 겨루면 DET가 앞선다. CLS의 값어치는 **DET가 배우지 않은
종류를 메우는 것**과 **관 밖 오탐을 막는 것**(OUT_CAR에서 DET 100% 오탐 vs
CLS 0%)이다.

## 4. 알아둘 것

**도메인이 성능을 가른다.** CLS는 야장 중심으로 배워 야장 판에서 이름 정확도
69.7%인데 S20/AIHub 판에서는 18.3%다. DET는 반대로 S20/AIHub에서 92.5%,
야장에서 33.3%다. **두 모델 다 자기가 배운 도메인에서만 제 성능을 낸다.**

실제 현장 영상은 야장 쪽에 가까우므로 **현장 성능은 위 숫자보다 낮게 봐야 한다.**

**모든 값이 잘라놓은 사진 판에서 나왔다.** 연속 실영상(카메라 이동·조명 변화·
대부분이 평범한 구간)에서의 검증은 하지 않았다 — 베타테스트가 다음 단계다.

**모델 파일은 저장소에 없다**(`.gitignore`의 `*.pt`, `*.onnx`). 클래스
이름표만 커밋돼 있고, 다른 PC에서는 파일을 옮기거나 §1.4 명령으로 다시 뽑는다.
